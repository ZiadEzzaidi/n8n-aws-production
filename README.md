# Self-hosted n8n in production on AWS: Terraform, HTTPS, secrets, tested restore

Case study: running the n8n automation platform on a single AWS server the way a small business would need it: reachable over HTTPS on its own domain, with no password stored in the code, no SSH port open, and a database backup that has actually been restored.

## The problem

n8n stores two kinds of things a business cannot afford to lose: its workflows, and the credentials those workflows use (API keys, passwords for Gmail, CRMs...). The goal was to:

- deploy it on AWS from code, so the server can be rebuilt or deleted with one command
- keep every secret out of the repository and off the developer's laptop
- serve it over HTTPS on a real domain name
- back up the data **and prove the backup restores**, with a measured downtime

## Architecture

```
Browser ──HTTPS 443──▶ [Security group: 80 + 443 only] ──▶ EC2 t3.micro (Amazon Linux 2023, Docker)
                                                              │
                                     Caddy (Let's Encrypt) ──▶ n8n 2.42.6 ──▶ PostgreSQL 16
                                                              │
                         reads 2 secrets at start ◀── SSM Parameter Store (SecureString)

Admin from the laptop ──AWS Systems Manager──▶ server   (no SSH port)
```

## What was built

| File | Role |
|---|---|
| `compose.yaml` | PostgreSQL, n8n (pinned version) and Caddy. n8n listens on `127.0.0.1` only: the outside world reaches it through Caddy |
| `Caddyfile` | HTTPS reverse proxy; Caddy obtains and renews the Let's Encrypt certificate by itself |
| `infra/main.tf` | Server, firewall, IAM role, and the two secrets (Terraform) |
| `infra/configure.sh.tftpl` | Writes the config on the server and (re)starts the stack. Used at first boot and for updates |
| `infra/user-data.sh.tftpl` | First boot: installs Docker and Compose, then runs the configure script |
| `scripts/deploy-server.ps1` | Applies a config change or an n8n upgrade to the running server, in place, through Systems Manager |
| `scripts/backup.ps1`, `scripts/restore.ps1` | Database dump and restore for the local stack |
| `.env.example` | The configuration n8n needs, for a local run |

### Security choices

- **Secrets generated by Terraform, stored encrypted in SSM Parameter Store.** The PostgreSQL password and the n8n encryption key are never written in the repository. The server reads them when it starts.
- **Least privilege:** the server's IAM role can use Systems Manager and read its own two secrets, nothing else.
- **No SSH.** Administration goes through AWS Systems Manager. IMDSv2 is required, and the disk is encrypted.
- **Firewall:** only 80 (certificate validation, redirect to HTTPS) and 443 are open. n8n's own port is not exposed.
- **The server holds the data, so Terraform never replaces it** because a newer AMI or boot script appeared (`lifecycle { ignore_changes = [ami, user_data] }`). Upgrades are applied in place.

## Run it locally

```powershell
copy .env.example .env      # then set POSTGRES_PASSWORD and N8N_ENCRYPTION_KEY
docker compose up -d
```

n8n is then on http://localhost:5678.

## Deploy it on AWS

Requirements: Terraform ≥ 1.6, AWS CLI v2 signed in, a domain name (a free DuckDNS subdomain works).

```powershell
cd infra
terraform init
terraform apply -var "domain=<your-domain>"
```

Then point the domain's DNS A record to the `public_ip` output. Caddy gets the certificate on its own once DNS resolves.

| Task | Command |
|---|---|
| Apply a config change or upgrade n8n | Change `n8n_version` in `infra/variables.tf` → `terraform apply` (updates the stored configure script; the server is not replaced) → `./scripts/deploy-server.ps1 -AwsProfile <profile>` |
| Delete everything | `terraform destroy -var "domain=<your-domain>"` in `infra/` |

## Backup and restore

The dump does **not** contain `N8N_ENCRYPTION_KEY`, which makes stored credentials readable. Here the key lives in Parameter Store, separately from the database: both are needed to recover. But Terraform manages that parameter too, so `terraform destroy` deletes the key along with the server: keep a copy of it outside AWS (a password manager) before tearing anything down.

**Local stack:**

```powershell
./scripts/backup.ps1                                   # writes backups/n8n-<timestamp>.dump
./scripts/restore.ps1 -BackupFile backups/<file>.dump  # stops n8n, restores, starts it again
```

**On the server**, the same steps run through Systems Manager (`aws ssm send-command`, document `AWS-RunShellScript`):

```bash
# Backup
cd /opt/n8n && mkdir -p backups
docker compose exec -T postgres pg_dump -U n8n -d n8n -Fc -f /tmp/n8n.dump
docker compose cp postgres:/tmp/n8n.dump backups/n8n-$(date +%Y%m%d-%H%M%S).dump
docker compose exec -T postgres rm /tmp/n8n.dump

# Restore
docker compose stop n8n
docker compose cp backups/<file>.dump postgres:/tmp/restore.dump
docker compose exec -T postgres pg_restore -U n8n -d n8n --clean --if-exists --no-owner /tmp/restore.dump
docker compose exec -T postgres rm /tmp/restore.dump
docker compose start n8n
```

## Restore test (23 October 2026, on the live server)

A backup nobody has restored is only a hope. The test:

1. Create a workflow `restore-test` and a credential `restore-test-cred` (Header Auth).
2. Back up the database.
3. Delete both, then confirm in the database that they are gone.
4. Restore, timing from "stop n8n" to "n8n answers its health check again".
5. Open both in the browser.

Results:

| Step | Result |
|---|---|
| Backup | 8.9 s end to end, dump of 517,614 bytes |
| After deletion | `workflow_entity`: 0 rows, `credentials_entity`: 0 rows |
| Restore | **70 s of downtime**, end to end, no error |
| After restore | both rows back; the workflow opens, and the credential opens without a decryption error, so the encryption key still matches |

```
Success n8n repond a nouveau
     name
--------------
 restore-test
(1 row)

       name
-------------------
 restore-test-cred
(1 row)
```

**Trap found during the test:** deleting a workflow in n8n first **archives** it. An archived workflow is still in the database, so the "disaster" would not have been real. It must be deleted from the archive too.

## Incident: owner-IP-only firewall

- **First design:** the security group allowed traffic only from the owner's IP address.
- **Problem:** HTTPS did not work with it. Let's Encrypt validates the domain by connecting to the server on port 80 from its own servers, which were blocked.
- **Fix:** open 80 and 443 to everyone. Port 80 only serves the validation and the redirect to HTTPS; n8n stays behind its login page, over HTTPS only.
- **Trace left in the code:** the security group description still reads "from the owner IP only", because AWS cannot edit a description without replacing the group.

## What I learned

- **Secrets:** where they come from (generated by Terraform), where they live (Parameter Store, encrypted), and who can read them (only the server's role). The n8n encryption key is as important as the database: without it, the restored credentials are unreadable.
- **Backups:** never keep two copies in the same place. Today the dump sits on the server's own disk, so it would disappear with the server. That is the first thing to fix.
- **Test the restore, not just the backup**, and measure it: 70 s is a number a client can plan around.

## Scope and next steps

Single server, single environment, deployed from 14 to 23 October 2026, then torn down. A production setup would add:

- a copy of every dump off the server (S3 with a lifecycle rule), scheduled automatically
- a copy of the encryption key outside Terraform, so that destroying the infrastructure cannot destroy the only key
- remote Terraform state (S3, encrypted): the local state file contains the generated secrets, which is why it is excluded from git
- monitoring and alerting on the health check
